# Self-hosted relay deployment

Run the existing `infra/relay` stack on your own machine with your own identity provider.
Two modes share one codebase:

- **Local self-host (recommended, $0):** `alchemy dev` runs the Worker on local workerd with
  local queues, Durable Objects and R2 simulation, and Hyperdrive pointed at a local
  Postgres. No Cloudflare Workers, PlanetScale or Axiom account is needed. Cloudflare is
  only used for DNS, Tunnel (public ingress) and Pages (static web) — all free and
  unmetered.
- **Cloud deployment:** `alchemy deploy` provisions the hosted stack (Cloudflare Workers
  Paid, PlanetScale, Axiom). See the [relay README](../../infra/relay/README.md) and
  [T3 Connect setup](./connect-setup.md); they own the Clerk and provisioning details.

## Identity provider

Use your own Clerk application (a free development instance is enough). Create the
`t3-relay` JWT template (`aud: t3-code-relay`) and the public CLI OAuth application exactly
as in [T3 Connect setup](./connect-setup.md). A self-hosted IdP (Logto/Authentik) is out of
scope: the Clerk SDK is integrated in the relay, web, server and mobile clients, so
replacing it is a rebuild, not a deployment.

## Local self-host

Prerequisites on the host machine: Node >= 24, pnpm (corepack), `cloudflared`, and a local
Postgres with a database for the relay, for example:

```sh
brew install postgresql@17 cloudflared
brew services start postgresql@17
createdb relay
```

Configuration lives outside the repository, for example
`~/.config/t3-relay-selfhost/relay.env`:

```dotenv
RELAY_API_ZONE_NAME=example.com
RELAY_TUNNEL_ZONE_NAME=example.com
CLERK_PUBLISHABLE_KEY=pk_test_...
CLERK_SECRET_KEY=sk_test_...
CLERK_JWT_AUDIENCE=t3-code-relay
APNS_ENABLED=false
RELAY_AXIOM_ENABLED=false
RELAY_DEV_DATABASE_URL=postgres://relay@127.0.0.1:5432/relay
T3CODE_RELAY_CLIENT_CONFIG_ENV=/path/outside/repo/client.env
ALCHEMY_TELEMETRY_DISABLED=1
```

- `RELAY_AXIOM_ENABLED=false` skips every Axiom resource; trace export and client tracing
  are disabled and mobile telemetry forwarding stays inactive.
- In local mode the stack skips PlanetScale entirely; Hyperdrive uses
  `RELAY_DEV_DATABASE_URL` as its dev origin. Apply the generated migrations once,
  in order (`--> statement-breakpoint` lines are SQL comments, so `psql -f` runs each file):

  ```sh
  cd infra/relay
  for d in migrations/postgres/*/; do
    psql "$RELAY_DEV_DATABASE_URL" -v ON_ERROR_STOP=1 -f "$d/migration.sql"
  done
  ```

Run the stack (keep it alive under a process supervisor for a real deployment):

```sh
vp run --filter t3code-relay exec alchemy dev -- --env-file ~/.config/t3-relay-selfhost/relay.env
```

`alchemy dev` prints the local Worker URL. Point a free Cloudflare Tunnel at it so the
relay has a stable public origin:

```sh
cloudflared tunnel create t3-relay-selfhost
cloudflared tunnel route dns t3-relay-selfhost relay.example.com
cloudflared tunnel run --url http://localhost:<worker-port> t3-relay-selfhost
```

Cloudflare credentials for the tunnel/DNS API resolve from Alchemy profiles
(`~/.alchemy/credentials/`, OAuth with automatic refresh) or `CLOUDFLARE_API_TOKEN` +
`CLOUDFLARE_ACCOUNT_ID`. The mint signing key pair is generated by the stack and stored as
Worker secrets; never write it to a file.

## Static web hosting

Build `apps/web` with the public values of your deployment (process env wins over repo env
files) and host `apps/web/dist` on any static host, for example Cloudflare Pages (free,
unmetered requests):

```sh
VITE_T3CODE_RELAY_URL=https://relay.example.com \
VITE_CLERK_PUBLISHABLE_KEY=pk_test_... \
VITE_CLERK_JWT_TEMPLATE=t3-relay \
VITE_CLERK_CLI_OAUTH_CLIENT_ID=<public OAuth client id> \
vp run --filter @t3tools/web build
wrangler pages deploy apps/web/dist --project-name <name>
```

## Linking devices

Per device, run the environment server with runtime overrides (no rebuild needed for the
bundled server; a source checkout reads the same variables):

```dotenv
T3CODE_RELAY_URL=https://relay.example.com
T3CODE_CLERK_PUBLISHABLE_KEY=pk_test_...
T3CODE_CLERK_JWT_TEMPLATE=t3-relay
T3CODE_CLERK_CLI_OAUTH_CLIENT_ID=<public OAuth client id>
```

Then `t3 connect link` (browser authorization; headless devices use the device grant or an
SSH-forwarded loopback port 34338) and start the server. `t3 connect status` reports the
relay URL and reachability. The managed tunnel needs `cloudflared` on PATH or
`T3CODE_CLOUDFLARED_PATH`; `--publish-only` links without a managed tunnel when devices
reach each other out of band (LAN, Tailscale).

## Rollback

One step per device: `t3 connect unlink`, then restart the server without the override
variables (default hosted configuration) and `t3 connect link` again. Stop the local
`alchemy dev` process and the tunnel to tear the self-hosted instance down. The hosted
relay and its defaults are untouched by this deployment.
